## What this is

Marketing site for **Things 4 Good** — the Thingelstad family's annual handmade-candle fundraiser. It is a static [Eleventy](https://www.11ty.dev/) v3 build on `things4good.xyz`, hosted on S3 and CloudFront (see "Deploy"). There is no client framework and no build step beyond Eleventy itself. The one backend is the small order service behind `/api/` (see "Order service"), which stays closed until Jamie turns it on; everything else is static.

Pages, each a `src/*.njk` that extends `base.njk` (Eleventy emits `<name>/index.html`, served at `/<name>/`):
- `index.njk` — long-scroll home page (the only one at `/`)
- `maker-night.njk` — Maker Night event page. Gated by `site.makerNight`, on since 2026-11-02 for the first one, Thursday, January 21, 2027 (`site.makerNightDate`, with `makerNightDateShort` in the nav, `makerNightTime` and `makerNightDonation`; every page reads them from there). How it works (Jamie, 2026-11-02): six Golden Ticket candles, each in a scent made only for them, are sold at the fall sale (or by preorder) for the donation, and the buyer takes theirs home that day; buying one is the seat, and two bring a friend (two per person at most, per the preorder form). On the night a thank-you candle made ahead waits for each guest, and they pour four of their own in any scents from the library; those must set and are picked up later. The date is fixed. The donation is divided evenly across the four causes. Name, email and phone are taken at purchase. If all six sell before the sale a second night may follow; the site does not say so. **Seats left** come from `src/_data/makerNightSeats.json` (`total`, `sold`): the nav, the hero flames and badge, the Spots row, the closing section, the home teaser and `llms.txt` all count down from it, and at 0 left the page says Sold out and drops the get-a-seat and preorder prompts. **The count follows Grist** (Jamie, 2026-11-07): the **Maker Night seats from Grist** workflow (`.github/workflows/maker-night-seats.yml`, running `scripts/maker-night-seats.mjs`) reads the Golden Ticket's Left from the order service's `GET /api/seats` every 15 minutes, the same number the order form sells against, and when it has changed it rewrites `sold` (`total` stays the page's six, and Left never shows more), commits the file to `main` and starts the deploy itself, because a push made with `GITHUB_TOKEN` starts no other workflow. ## Voice

The site's copy follows Jamie's blog voice, in the third person (rewrite of 2026-11-05, on Jamie's approval line). Jamie on the first samples: "This is good but it should be in 3rd person not 1st person."

- Name Jamie: "Jamie writes up every sale on the blog." Never "I", never a signed "- Jamie". "We" stays for the family. Use family members' names rather than pronouns.
- Everyday words ("folks", "it turns out", "non-profit" with the hyphen), literal headings, the number and then a reaction, the mess left in (the first batch's 20x fragrance stays), sincere exclamation points. Em dashes are not banned; Jamie uses them too.

## Architecture

Eleventy config lives in `.eleventy.js`. Key conventions it sets:
- Input is `src/`, output is `_site/` (git-ignored). Includes in `src/_includes`, data in `src/_data`.
- Both HTML and Markdown render through **Nunjucks** (`htmlTemplateEngine` / `markdownTemplateEngine` are `njk`).
- `base.njk` links `/styles.css?v=<hash>` (the `assetVersion` filter), because browsers keep the stylesheet a while (five minutes, `scripts/publish-plan.mjs`; GitHub Pages, the host until 2026-10-27, gave it ten). Without the hash, a fresh page arrived with last deploy's stylesheet and the candles drew as bare grey buttons (10-25). CloudFront's cache key ignores the query, so the hash only steers browsers; each deploy clears CloudFront.
- `src/styles.css`, `src/favicon.svg`, `src/robots.txt`, and anything under `src/images/` are passthrough-copied to the site root unchanged. `src/images/README.md` is explicitly ignored from the build.

### Templating

`src/_includes/base.njk` is the single layout. Every page does `{% extends "base.njk" %}` and fills named blocks rather than passing a `layout:` in front matter. The blocks the base exposes: `head` (extra `<head>` tags), `brandHref`, `navLinks`, `navDate`, `navCta`, `content`, `footerExplore`, `subscribeHref`, `scripts`. Page front matter sets `title` and `description` (both consumed by `<head>`); the canonical link and the share tags (Open Graph, a large Twitter card) are built from those and `page.url`, so a page never sets them.

**Share cards.** A page with a `card` in its front matter shares a card drawn by cards.thingelstad.com (2026-10-25, Jamie's direction B: the site's own type over a candle photo, the band naming the family). `card` holds `kicker` (the page's eyebrow), `name` (its heading), `accent` (the heading's last words, set apart: "100% for good."), `summary` (a line under it), `photo` (a file in `src/images/cards/`, cut to 1200 x 562, the card's photo area; the card maker fetches no other photo) and `saleFacts: true` for the sale's date, city and price as pills, from `site.json`. `base.njk` publishes those as the page's h-entry (`<data>` elements at the end of `<main>`, which is all the card reads) and points `og:image` at `https://cards.thingelstad.com/t4g/<page>.png?v=<v>` (`index` for the home page), with `v` the first 10 hex of the SHA-256 of the fields (the `cardFields` and `cardVersion` filters in `.eleventy.js`), so changing what the card says draws a new card. No running totals on a card: they change. A page without `card` (Maker Night, the 404) keeps the plain candle photo. The card maker's side is `~/Projects/thingelstad.com/cards.thingelstad.com` (its `t4g` entry); a new card field needs it there first.

**The nav and footer are canonical defaults in `base.njk`** — `navLinks` (Fundraiser · Candles · Impact · Numbers · Maker Night when `site.makerNight` · FAQ), `navDate` (`site.saleDates`), `navCta` (the Get updates button, to the Buttondown list), and `footerExplore` (6-item list) all have real default content. Pages inherit them automatically; a page overrides a block only to deviate — typically `navLinks` to add `aria-current="page"` on its own item, or `brandHref`/`navCta` for page-specific behavior. Subpages set `brandHref` to `/`; the home page keeps the default `#top`. When changing site-wide nav/footer, edit the defaults in `base.njk`, not each page.

`base.njk` also contains the only JavaScript on the site, inline near the bottom: an animated number counter (driven by `data-target` on `#counter`) and an `IntersectionObserver` that adds visibility to elements with the `.reveal` class on scroll. Tinylytics analytics loads only if `site.tinylyticsSite` (the site id) is set.

**Tinylytics kudos and events** (2026-10-25, Jamie's go). The tag is Tinylytics' one script for every site, `<script defer src="https://tinylytics.app/js/script.js" data-site="…">`, with no query parameters (since 2026-11-02). Events, automatic events and kudos (with an empty symbol, the old `kudos=custom`) are switched on in the site's Tinylytics settings, not in the URL.
- *Kudos:* every card on `/impact/` has a candle button, a plain pill of a flame and a count (Jamie, 10-25: "keep the design to a simple button with a counter"). Its title and aria-label say "Light a candle for <name>". It is a Tinylytics kudos with `data-path="/impact/<slug>/"`, the path the designed-for per-org pages would take, so each nonprofit keeps one count across years.
  - The embed writes only the count into the button, so the flame is drawn by CSS (`.candle-kudos::before`, Lucide's flame as a mask): an outline until this browser lights it (`.did_select`), then filled.
  - The button starts with the text `0`. The count endpoint answers only for paths that already have a kudo, and the embed leaves the button's text alone otherwise.
  - The embed wires kudos buttons once, when the page loads. That is why the Impact script draws every card once and filters by hiding and reordering them. Never go back to rebuilding the grid's HTML, or the candles go dead after the first filter change.
- *Events:* auto mode counts outbound links (`link.outbound`, value = host). Hand-tagged events, via `data-tinylytics-event` + `data-tinylytics-event-value`:
  - `updates.click`: every Get updates link. The value names the spot (`nav`, `footer`, `home-hero`, `home-when`, `home-subscribe`, `impact-close`, `faq-when`, `faq-ask`, `preorder-steps`, `preorder-close`, `event-head`).
  - `nonprofit.visit`: the value is the org slug.
  - `order.link`: every link to `/order/`; the value is where it sits (`nav`, `home-hero`, `home-next`, `preorder-head`, `preorder-steps`, `faq`, `candles`, `maker-night-details`, `maker-night-reserve`, `event-head`, `event-close`). It replaced `preorder.sheet` (the Google Form) on 2026-11-07. While a window is open the header button is Preorder (or Order candles after the sale) and the home hero's primary button goes to the form; shut, they go back to Get updates, which then owns the `nav` and `home-hero` spots of `updates.click`. During the sale weekend the header button is Sale this weekend, to `/<year>/`.
  - `chart.year`: the home and Numbers year links. The value is the year.
  - `faq.open`: the value is a question key. A small script in `faq.njk` keeps the event on closed questions only, so closing one is not counted.
  - A new subscribe link gets an `updates.click` tag with a new spot name. A tagged link is not also counted as `link.outbound`.
  - Everything is anonymous and counted per click, never per person.

### Content is data-driven — events → supported nonprofits, everything else computed

The model is **sale events, each allocating its exact total to a set of nonprofits**. There is one hand-edited dataset of events plus a small config file; every total, count, growth rate, chart height, grand total, and candle-math figure is *derived* in `metrics.js`. **Never hardcode a derived number in a template, and never duplicate event/org facts** — that's the mistake this layer was built to prevent (the home and stats charts had already drifted apart).

- **`events.json`** — the single source of truth: `events[]`, one record per sale event. Fields: `slug`, `kind` (exactly `"candle-sale"` or `"special-event"`), `year`, `name`, exact `raised` total, and (candle-sale only) `candles` + `participants`. Each event nests `supported[]` — its nonprofit allocations: `slug` (stable org key, matches the logo filename), `name`, `logo`, `url`, `who` (family-member picker, or `"Everyone"` for collective/special-event recipients), `amount`, `blurb`, `reason` (`""` when none). The annual **candle sale** is the only `kind` that splits across multiple nonprofits; **special events** (the holiday market, Maker Night) each support one. Per-nonprofit `amount`s come from each year's tally and sum to the event's exact `raised`. Jamie, 2026-11-06: "they are pretty exact but there could be reconciliation issues", so they print to the cent with no `(est.)` marker.
- **`metrics.js`** (computed, CommonJS) — `require()`s `events.json` + `site.json` and exports the `metrics` global. Candle-sale events drive `perYear[]` (`cumulative`, `growthPct`/`Display`, stacked-bar `candleHeightPct`/`eventsHeightPct`/`barHeightPct`, `yearTotal`, `isLatest`, `slug`) — **cumulative & growth are candle-sale only**; special events add only the stacked segment + the grand total. Also exports `totalRaised` (candle), `eventsTotal`, `grandTotal` (+`Display`s), `nonprofits` (flattened allocations enriched with `year`/`eventKind`/`eventName`/`event`, feeds the Impact list + home logo-wall), `eventList` (Impact event filter), `orgCount`, `records`, `candleMath`, `raisedStats`, `footStats`, `pricePerCandle`. **All display formatting is done here via `toLocaleString`, so templates stay dumb** — no number filters in `.eleventy.js`.
- **`candles.json`** — this year's lineup, hand-edited from the scent markers printed for the sale: `scents[]` (`slug`, `name`, `description`, `art`, a scent with no `art` shows a New frame until its label is ready; `makerNight: true` prices the card at `site.makerNightDonation` and links it to Maker Night), `secretScents` (true shows an "under wraps" card and a line on the home page and in `llms.txt` for the new scents held back until the sale; set it false and add them once revealed), and `extras[]` (`slug`, `name`, `description`, `donation`). A regular candle's donation is `site.pricePerCandle`, never repeated here. Descriptions are plain Unicode (curly quotes, em dashes), not entities, so `llms.txt` prints them as is. The art is Mazie's label drawings in `src/images/scents/`, cut from the marker sheet's PDF into 640px palette PNGs in label ink (`#111`) on transparency, about 25 KB each. The cards are drawn like the jar labels (white stock, black ink, American Typewriter with Courier Prime as the fallback). A new scent needs its drawing there in the same form. The card is a one-column CSS grid, not a flex column: Safari stretches an `aspect-ratio` box inside a flex column, which made the art change size as the page scrolled. The XL size is an extra with no scents named, on purpose (Jamie, 2026-11-06: "don't list").
- **`site.json`** — true global config: `name`, `email`, `saleDates`, `saleYear`, `makers[]`, `blogUrl`, `orders` (the order window, see "Order windows"), feature toggles (`tinylyticsSite`, `makerNight`, with `makerNightDate`, `makerNightDateShort`, `makerNightTime`, `makerNightDonation`), plus the candle-sale constants moved out of the event data: `pricePerCandle`, `candleConstants` (wax/wick/burn per candle), `tightestRace`.

To change fundraiser facts you almost always edit `events.json` (or `site.json` for constants) and rebuild. A new fundraising occasion is a new event object; record Maker Night results by adding a `kind:"special-event"` event for the year. Note some JSON/JS string values carry HTML entities (`&amp;`, `&middot;`) rendered with `| safe` — keep that style. Gotcha: during `eleventy --serve`, editing the JSON re-runs `metrics.js` on rebuild; if numbers ever look stale, restart `npm start`.

**Future per-org pages** (`/impact/<slug>/`) are designed-for but not built: add a `src/organization.njk` paginating over `metrics.nonprofits` (`size: 1`, `permalink: "/impact/{{ org.slug }}/"`); the `slug` field already exists for this.

### Styling

A single hand-written `src/styles.css` (~480 lines), no preprocessor or utility framework. Design tokens (color names like `--marigold`, `--pine`) are CSS custom properties. Fonts (Newsreader, Hanken Grotesk, Caveat) load from Google Fonts in the `<head>`.

## Deploy

`.github/workflows/deploy.yml` tests and builds with Node 24 on every pull request and push. A push to `main` publishes the tested build to S3 and CloudFront in the `deploy-aws` job. There is no staging environment — `main` is production.

### S3 and CloudFront

The site moved from GitHub Pages to S3 and CloudFront on 2026-10-27 (Jamie: "Approved: move things4good.xyz, poapkings.com and rwbookclub.com from GitHub Pages to S3 + CloudFront"), copying the shape escape.thingelstad.com took on 2026-10-26. `things4good.xyz` and `www` point at the distribution; GitHub Pages, `src/CNAME` and the Pages setting are gone.

Four stacks, generated by `infra/templates.mjs` into `infra/generated/` (`npm run infra:generate`; a unit test fails when the committed JSON is stale) and deployed **from this Mac as the cloud-engineer identity** with `npm run infra -- certificate|site|delivery|orders` (`--plan` prints the change set and stops). `infra/deployment.json` records their names, tags (`Project=things4good`) and outputs.

- `things4good-certificate`: one ACM certificate for `things4good.xyz` and `www.things4good.xyz`, validated by two CNAMEs at Namecheap (`npm run infra -- certificate` prints both, and again on a rerun). DNS is Jamie's to edit. Keep both records: renewal needs them. ACM checks CAA along each name's CNAME chain, and GitHub's CAA refuses Amazon, so a name cannot validate while it is a CNAME to `jthingelstad.github.io` (for the first issue, Jamie gave `www` A records during validation).
- `things4good-site`: a private, versioned bucket (old versions kept 90 days) behind CloudFront with origin access control; AWS's CachingOptimized policy (no query string in the key, so `?ref=` and `?v=` share one copy); security headers plus `Access-Control-Allow-Origin: *` as GitHub Pages sent; 403/404 serve `/404.html`; access logs to CloudWatch Logs (`/things4good/web-access`, 24 months (731 days), JSON, no viewer IP and no query string). Its 5xx alarm was removed in Jamie's 2026-11-03 alarm cut. The aliases (apex and www) and the certificate attach only when the certificate is ISSUED (`npm run infra -- site` checks). The distribution uses the shared `edge` web ACL (projects-sysadmin `edge-waf` stack; rules count only until tuned).
- `things4good-orders`: the order service (see "Order service"). The site stack reads its function URL, so this one goes first.
- `things4good-delivery`: the role GitHub Actions assumes (`vars.AWS_DEPLOY_ROLE_ARN`), `main` only. It can publish into the bucket and clear the cache; it cannot change the stacks.

The viewer-request function (`infra/viewer-request.mjs`) sends any `www.` host to the apex with one 301 that keeps the path (in its slash form) and the query string, sends a bare path to its slash form, and serves `index.html` for directory URLs. There is no redirect map.

**Content types and caching** are set per file by `scripts/publish-plan.mjs`: every file is five minutes in browsers and a day in CloudFront, which every deploy clears. `tests/e2e/built-site.cjs` (`npm run test:e2e`, after `npm run build`) fails when the build writes a file the table does not type, so a new kind of file needs an entry there.

`npm run deploy:aws` (`scripts/deploy-aws.mjs`) refuses unless the site stack's live template equals `infra/generated/site.json`, so infrastructure goes out first, on its own. It uploads the files whose MD5 changed (`--all` re-uploads everything, needed after a `publish-plan.mjs` change), deletes what the build no longer writes, clears the cache, and reads the result back through the CloudFront domain (the front page as built, a deep page, the stylesheet's and sitemap's types, the slash form, a 404). The deploy assumes the delivery role through GitHub's OIDC token; no AWS keys are stored.

### Order service

`infra/order-service.mjs`, one Lambda function behind `things4good.xyz/api/`, built 2026-11-07. `GET /api/stock` returns the window and the current event's products, prices, quantity left and the most one order can take (`limit`), cached five minutes at the edge, one minute in browsers, and no buyer data. `POST /api/order` validates, re-reads stock from Grist, writes the order and returns the total. `GET /api/seats` returns the Golden Ticket's `{event, total, left}` in every window, cached the same way, for the seat sync; it is the one route that reads Grist while orders are shut.

**Order windows (Jamie, 2026-11-07).** The sale runs two weeks. `site.json`'s `orders` drives the service and the pages:

- `window`: `preorder` (order ahead, opened by hand about a week before the sale), `paused` (the sale is on, or its paper sheets and recount aren't in), `after` (the leftovers week, opened by hand once the recount is in) or `closed` (the rest of the year).
- `closes`: when an open window shuts, with its offset (`2026-11-15T23:59:00-06:00`). A preorder window becomes `paused` at that minute and a leftovers week becomes `closed`, with no deploy: the service checks every request (`currentWindow`), the order page believes the service, and the nightly build (06:07 UTC in `deploy.yml`) brings the nav and other pages along. Preorders close at 11:59 p.m. the night before the sale; the leftovers week seven days after it opens, at 11:59 p.m. Central. GitHub turns off a public repo's schedule after 60 days without a commit, so check the Actions tab before a window opens.
- `goldenTicket`: puts the Golden Ticket on the form, two to an order, and the Maker Night page's links to it. On since 2026-11-07, once the seat count followed Grist. Everything else the event offers is always on.
- `saleEnds`: picks the paused message ("Come see us at the sale" until then, "We're counting what's left" after). `reopens`: optional words for when orders come back ("Monday, Nov 9"); empty says "soon".

In a preorder window regular candles have no cap (`left: null`, 24 a line): the family pours to fill them, and Left going below zero in Grist is the list to pour. Everything else (XL candles, lids, the Golden Ticket) is capped at Left in both windows, so a count Grist doesn't have yet, like paper sheets from the sale, can oversell them. The Golden Ticket sells two to an order while seats remain, when `goldenTicket` is on, and the Maker Night page's count follows the same Left (see `maker-night.njk` above). **Before opening the leftovers week, the numbers have to be right:** Left means nothing until all the paper sale sheets are entered and a recount is recorded in `Made` or `Adjustment`.

2026: the order form replaced the Google Form on Nov 7, mid-sale, taking preorders through Sunday, Nov 8 at 11:59 p.m. (Jamie: "a way better user experience"), regular candles only at first; XL candles and lids went on the same day (Jamie: "Lids and Xl should be on the form"), and so did the Golden Ticket once the seat count followed Grist. Then paused until Jamie says the recount is in.

To change the window: edit `orders`, run `npm run infra -- orders` (which sets the function's `ORDERS_WINDOW`, `ORDERS_CLOSES` and `ORDERS_GOLDEN_TICKET`, and `ORDERS_CAUSES` from `causes.json`, and refuses an open window without a future `closes`), and merge (which builds the pages). To shut early, run the infra step first, so orders stop before the pages change. Shut, the stock and order routes answer `503 {"open":false,"window":...}` before any call to Grist; seats still answer.

**The rules it keeps:**
- Reserved concurrency 1, so a stock check and its write never overlap and two buyers can't get the last candle. The price is a 429 from Lambda while another request runs, which the page retries, with the same request id.
- Prices and availability come only from Grist. Short stock answers 409 naming what's short and writes nothing. A product the window holds back is `422 unknown-product`; a third Golden Ticket is `422 invalid`.
- Name, email and mobile are required. Mobile since 2026-11-07 (Jamie: "helpful for followup"), with seven digits at least, on the page and in the service.
- A buyer matches a person on exact email only, ignoring case. An existing person is never overwritten, only blanks filled, and the answer looks the same either way: same body, and never sooner than a three-second floor, because the two paths take different numbers of Grist calls.
- The page sends a request id, kept in `Source_Row` as `web <uuid>`, and a repeat answers the same total without writing. Changed answers get a new id.
- Turnstile (Jamie, 2026-11-07): the Cloudflare widget "Things 4 Good order form", site key in `site.turnstileSiteKey`, managed mode, set to things4good.xyz and www. The page loads it only once stock shows, with `appearance: interaction-only`, so most buyers never see it. Every order carries a token, checked with siteverify after the form's own checks (so a typo spends no token) and before any call to Grist, along with the hostname and the action `order`. A refused token is `422 {"error":"turnstile"}`, never a 403, and the page resets the widget after any answer but success. A token is good once, so a request id that passed is let through without one for 15 minutes; that is what lets the page resend an order after a 503. Siteverify down, or refusing our secret, is a 503 and an alarm: orders fail closed without Turnstile.
- Spam, besides Turnstile: a hidden `website` field, 24 a line and 30 an order, 5 orders and 20 tries an hour per address, 30 orders an hour overall, and limits on every field. The counts live in memory, which works because concurrency 1 means one environment; they reset when Lambda replaces it.
- Logs are outcomes only: no name, email, phone, note or address, and never the text of a Grist error. A unit test holds this. An alarm (`things4good-orders-errors`, to `projects-sysadmin-alarms`) fires on anything logged at level `ERROR` or on Lambda's own `Errors`.
- An order writes `Order_Type` "Preorder" or "After the sale" (by window) and `Fulfillment_Method` "Pickup" or "SPS delivery", and leaves `Sale_Order` to its trigger. The form shows every cause checked, and a buyer unchecks any to leave out (Jamie, 2026-11-07: "By default, they should all be selected"); at least one stays. All of them writes `Causes` blank, which splits the order evenly across the four and prints as ALL on the pick sheet; fewer are written as picked, in `causes.json` order. A page from before the choice sends none, which is blank too. An uneven split is still for purchases at the sale. An order holds stock before it's paid; Jamie removes unpaid ones by hand. The service sends no email of its own.
- The list (Jamie, 2026-11-07: "make sure any user that does this is also added to Buttondown emails"): each new order, never a repeat, adds the buyer to the Thingelstad Family list (`things4good` on Buttondown) as `type: regular`, so no confirmation email, with the note "Added by the order form" and the buyer's IP for Buttondown's firewall. The page says so under the button. No collision header, so an address already there, unsubscribed included, is left alone and never resubscribed. Not the bypass-firewall header either: it allows five an hour. A refusal (a bad address, the firewall) logs at `WARN` with Buttondown's code; a failure (the key, an outage) logs at `ERROR` and alarms. Neither ever fails the order, and the log's `list` field says what happened. No tags: the plan has none.

**Hosting traps, all handled in the templates.** `/api/*` has its own CloudFront behavior without the viewer-request function, which would send `/api/stock` to its slash form. The function URL takes only signed requests through origin access control, and for a POST CloudFront needs the viewer to send the body's SHA-256 in `x-amz-content-sha256`, so the page computes it. That header can't be listed in an origin request policy of our own (CloudFront refuses it), so the behavior uses the managed `AllViewerExceptHostHeader`, which AWS intends for function URLs: no viewer `Host`, so the signature is for the URL's own name, and it carries `CloudFront-Viewer-Address` for the rate limit. A POST without the hash comes back as the HTML 404, because the distribution's `CustomErrorResponses` turn any 403 or 404 into the site's 404 page on every behavior. That is also why the service answers only with 200, 400, 405, 409, 413, 422, 429, 500 and 503.

**The keys.** The secret `things4good/orders/grist` (named before it held more than Grist) holds `{"apiKey", "docId", "turnstileSecret", "buttondownKey"}`, so none is in the repo or a template. `apiKey` is the 1Password item `Grist API - Otto` (Jamie, 2026-11-07), not `GRIST_API`. `turnstileSecret` is the widget's secret, read with `cf turnstile widgets get <site key>`. `buttondownKey` is the 1Password item `Buttondown - things4good` (Jamie, 2026-11-07). Only the function's role can read the secret, by a deny in its resource policy, so to check it use the self-check `npm run infra -- orders` prints: it reads stock through the function and says which keys are there (`turnstile`, `list`), never their values, and fails without the Turnstile secret. A missing Buttondown key only means nobody is added. To set a new value, write all four at once, without printing any (the document id is in the t4g-candles repo):

```bash
export OP_SERVICE_ACCOUNT_TOKEN="$(cat ~/.otto/credentials/1password-service-token)"
export T4G_GRIST="$(op read 'op://Otto/Grist API - Otto/credential')"
export T4G_BD="$(op read 'op://Otto/Buttondown - things4good/credential')"
export T4G_TS="$(cf turnstile widgets get "$TURNSTILE_SITE_KEY" | jq -r '.secret // empty')"
jq -n --arg docId "$GRIST_ORDER_DOC" '{apiKey: env.T4G_GRIST, docId: $docId, turnstileSecret: env.T4G_TS, buttondownKey: env.T4G_BD}
    | if any(.[]; . == null or . == "") then error("a value is empty") else . end' \
  | AWS_PROFILE=cloud-engineer aws secretsmanager put-secret-value --secret-id things4good/orders/grist --secret-string file:///dev/stdin --query VersionId
unset T4G_GRIST T4G_BD T4G_TS
```

The function holds the keys for the life of its environment and reads them again if Grist, Turnstile or Buttondown turns one down, so a rotated key needs no deploy. A new `docId` does, or any configuration change that replaces the environment.

**Tests.** `npm test` covers the rules with a pretend Grist, a pretend Turnstile and a pretend Buttondown. For the page, Cloudflare's test site keys (`1x00000000000000000000AA` passes, `2x00000000000000000000AB` fails) work on any host, localhost included. `npm run test:orders` runs them against a real copy: it copies the document into the key's own workspace with `POST /docs/<id>/copy`, sets its own stock, uses made-up buyers, and deletes the copy whatever happens. It refuses to write to the live document's id. Never test against the live document. See the top of `tests/integration/orders-throwaway.mjs` for its variables.

**Deploying.** `npm run infra -- orders` deploys the stack, uploads `infra/order-service.mjs` and runs the self-check. A change to the service goes out only that way, not on merge, because the delivery role can't touch stacks or functions. After a change to the site stack, `npm run infra -- site` goes before the merge, since `deploy:aws` refuses when the live template differs.
